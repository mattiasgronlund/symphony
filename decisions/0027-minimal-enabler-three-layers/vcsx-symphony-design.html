Symphony · layering, topologies, config

A minimal credential broker; vcsx as a tiny VCS engine; an autonomous daemon that adds task management + a policy graph; the repo owns its Way of Working. Design sketch — not normative.

Governing principle. Symphony enables Ways of Working; it enforces none. Its one irreducible guarantee is the secret-isolation invariant: the agent never needs VCS or Forge credentials. Everything WoW-shaped is repo-owned config and configurable seams. vcsx is the optional reference engine; a 100%-custom WoW is just a different wiring.

vcsx ship/land and the daemon are two front-ends over one executor reading one repo.policy.toml — which is what makes them provably consistent. So vcsx is not tiny (it owns the executor); what stays tiny is Symphony's marginal code over it — task management + autonomous bindings + poll/dispatch.

Trust & config sourcing

The repo owns the WoW, so an operator configuring Symphony needs no WoW knowledge. Integrity comes not from a "do not edit" flag but from where Symphony reads each part.

Part of the WoWRunsRead fromWhy safe
before:commit gate (mise run check), scan-contentin-sandboxthe worktree (agent's branch)only affects the sandbox; can't escalate; correctly runs a PR's own gate change
host-side hooks, engine selection, policy graph, branch-name patternhost-sidethe protected base revisionagent can't push to base; WoW-trust = base-branch trust (review-gated)
scope invariant (work-branch-only, assigned-issue-only)host-sidebroker-core built-inalways enforced regardless of any config

Secret vs. integrity value. The broker secret store holds only outward credentials (forge/VCS/tracker tokens — the isolation invariant). The gate-cache HMAC is not a broker secret: it is a repo-internal integrity value ("raise the bar a little"), held in the repo's host-side hook environment, never broker-mediated.

Topology 1 — Daemon (autonomous, task-managed)

Tracker dispatches; the agent works under task management; completion is computed ("all tasks closed"), not asserted. The policy graph turns a conflict into an agent task and a need-help into a human escalation.

Topology 2 — Interactive agent, secrets secured

A human is present, so there is no task manager and no policy graph — the human drives vcsx ship/land with simple commands. The broker core still keeps the agent credential-less; escalations go to the human via typed results.

The action-policy machine (one executor, two front-ends)

One mechanism: (trigger) → (action), run by a single executor in vcsx. Hooks are not a separate axis — they are policy edges on lifecycle positions. The WoW edges are shared; only the initiator and the escalate binding differ per front-end (ship/land ↔ human, daemon ↔ agent task). Triggers and actions:

TriggersActions
before:commit, before:push, before:create_pr, before:merge (positions)
push:ok, push:non_fast_forward, integrate:merge_conflicts (typed results)
tasks:all_closed, task:#needs_help, task:closed (task state) 		run_op (a vcsx primitive) · run (a hook command)
escalate (abstract; bound per front-end) · create_task · set_state
notify · park · fail

Matching: most-specific-wins, with #class fallback

You never enumerate every code. Each outcome carries a proto class (done / needs_caller / error), giving fallback rungs:

push:non_fast_forward   # 1. exact reason
push:#needs_caller      # 2. any recoverable push outcome not named
push:#error             # 3. ANY other push error code
#error                  # 4. any error from any operation
<built-in default>      # 5. nothing matched → FAIL-SAFE (park/fail + surface reason),
                        #    NOT a silent no-op (that no-op is only for unmatched signals)

Configuration — two files

The repo expresses its WoW once; all topologies honor it. The operator config needs no WoW knowledge.

1 · repo.policy.toml — repo-owned (the WoW; vcsx.toml merged in)

repo.policy.toml 
# Host-side parts are read by Symphony from the protected BASE revision (the agent
# cannot push to base). The in-sandbox gate is read from the WORKTREE. vcsx
# (standalone) reads [engine] + the in-sandbox edges; ignores the policy graph.

[engine]                        # was vcsx.toml — engine choice is a repo decision
kind             = "vcsx"        # or "command" for a 100%-custom WoW
backend.prefer   = ["jj", "git"]
transport.kind   = "direct"      # "command" for an authorized-access remote
forge.kind       = "github"
base_branch      = "main"

[scope]
branch_pattern = "symphony/{issue.identifier}"  # the NAME is WoW; work-branch-only INVARIANT is built-in

# ---- In-sandbox edge (read from WORKTREE; agent-editable; cannot escalate) ----
[[policy]]
on = "before:commit"
do = { run = [["mise","run","check"], ["scripts/vcs/forbidden-token-scan","--pending"]],
       in_sandbox = true, block_on_nonzero = true }

# ---- The ship / land flow + hooks (SHARED: these edges DEFINE what ship/land do) ----
[[policy]]                       # host-side (read from BASE); was [hooks.after_push]
on = "push:ok"
do = { run = ["scripts/gate_cache_transport.py","publish","--branch","{branch}"],
       env = "GATE_CACHE_KEY",        # repo-internal integrity value — NOT a broker secret
       best_effort = true }

[[policy]]
on = "push:ok"
do = { run_op = "create_pr" }

[[policy]]                       # land-time: derive the squash message from the PR (title verbatim, body strip-linear)
on = "before:merge"
do = { run = ["scripts/vcs/forbidden-token-scan","--strip-linear"], transform = "pr_to_squash" }

[[policy]]
on = "push:non_fast_forward"
do = { run_op = "integrate_base" }

[[policy]]
on = "integrate:done"
do = { run_op = "push" }

[[policy]]                       # WoW names the NEED; the front-end binds the resolver
on = "integrate:merge_conflicts"
do = { escalate = "resolve-conflicts" }

[[policy]]                       # any other push error → park, surface the proto reason
on = "push:#error"
do = { park = "push-failed" }

[[policy]]                       # last resort across all operations
on = "#error"
do = { fail = true }

# ---- Autonomous driver (DAEMON only: what ship/land get from the human instead) ----
[driver]
on       = "tasks:all_closed"       # computed completion ...
run      = "ship"                  # ... runs ship — the same verb the interactive human types
escalate = { create_task = true, assignee = "agent" }  # interactive binds escalate → return to human

[[policy]]                       # resume after the agent closes the escalation task
on = "task:resolve-conflicts:done"
do = { run_op = "integrate_continue" }

[[policy]]                       # agent asked for help → escalate to a human
on = "task:#needs_help"
do = { set_state = "Blocked", notify = "human" }

# ---- Task seeding (DAEMON only) ----
[tasks]
seed_from_ticket = true            # derive from checklist / sub-issues when the tracker exposes them
plan_if_empty    = true            # else open with a planning turn
sync_to_tracker  = "if_supported"

# ---- Tracker workflow transitions (decision 0017) ----
[[tracker.transitions]]
from = "In Progress"
on   = "pull_request_opened"
to   = "In Review"

[[tracker.transitions]]
from = "In Review"
on   = "tasks:all_closed"
to   = "Done"

2 · symphony.operator.toml — operator-owned (no WoW knowledge needed)

symphony.operator.toml 
# Holds ONLY what enforces the secret-isolation invariant + where things are.

[secrets]                          # OUTWARD credentials only — scrubbed before the sandbox forks
provider      = "env"
vcs_token     = "GITHUB_TOKEN"      # the agent must never hold these
forge_token   = "GITHUB_TOKEN"
tracker_token = "LINEAR_API_KEY"
# gate-cache HMAC is NOT here — it is a repo-internal integrity value (repo-owned)

[sandbox]
profile = "strict"                # reference baseline: jai Strict (decision 0004)

[repo."acme/widgets"]
policy = "repo.policy.toml"        # the WoW lives in the repo; host-side parts read from base

A repo-owned WORKFLOW.md still carries the agent prompt (in-sandbox, worktree-read); the in-sandbox gate/scan it used to hold are now before:commit edges above.

For a different WoW, only repo.policy.toml changes — the broker core, the secret-isolation invariant, and the sandbox boundary are identical.
